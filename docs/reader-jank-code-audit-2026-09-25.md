用户确认纯文字和插图区域都有掉帧，至少上周末版本（应为 `+21`）已经出现。
因此本次重点查找补图之外、旧版已经存在的路径。

后续验证：[真实文章的 Mac 原生测试](reader-real-content-macos-2026-09-25.md)
已复现普通下载恢复中的帧启动阻塞，36 个逐本同步间隙均与慢帧重叠，证据指向
重复全量重建书架。随后已修复书架全目录投影、下载打开时的全库重建，
以及未变化目录的重复写入；
修复后对照也记录在该测试文档。以下保留最初代码审查时的判断，运行时结论以
该测试记录为准。

此前的 macOS 性能测试和测量报告已先提交为 `2579fe9`。最初审查阶段仅记录
结果，没有修改产品实现。对照基线为 `v1.0.0+21`（`9142848`）与 `2579fe9`。
下面的行号指向 `2579fe9`；旧版存在性通过读取 tag 源码核对。

## 结论与证据边界

确认了六类旧版已有的工作负载或布局风险。它们有明确的触发路径，但本次没有
新增运行时测量，不能将它们都称为已确认的鸿蒙掉帧根因。优先检查普通下载恢复
和章节预取中的同步处理；对于完全空闲、同一章中间的持续拖动，应单独检查
每帧锚点测量、文本布局和选择区域的成本。

| 优先级 | 路径 | 最相关的触发时机 | +21 已有 |
| --- | --- | --- | --- |
| 高 | 普通下载恢复：全目录写入、任务扫描、全书架重建 | 冷启动或回到 App 后阅读，尤其下载记录很多时 | 是 |
| 高 | 章节预取：同步缓存读取、全章校验、缓存写入 | 进入阅读、跨章或反向回读；长章节成本更高 | 是 |
| 中 | 滚动中扩展窗口、追加章节并重建索引 | 接近窗口末尾、跨章、快速连续阅读 | 是 |
| 中，需采样 | 每帧扫描挂载段落的几何位置 | 同一章内持续拖动；与后台下载无关 | 是 |
| 中 | 停止滚动后同步保存进度、写历史队列 | 松手、惯性停止、再次触摸中止惯性附近 | 是 |
| 中 | 插图首次解码后改变正文高度 | 未知尺寸插图首次进入预加载或可见区域 | 是 |

这些路径主要是共用 Dart/SQLite/Flutter 代码，因此不是鸿蒙专属代码；但平台
实际成本和呈现表现仍需各自测量。不能从 Mac 小样本推断鸿蒙无问题，也不能
在没有真机栈证据时归因到鸿蒙引擎。

## 1. 普通下载恢复的同步工作没有随后台任务一起移出界面线程

调用链：`main.dart:709` 的 `_resumeDownloadIntents` 在启动、恢复到前台时遍历
所有启用的下载意图，逐本进入 `_synchronizeIntent`。

- `novelia_download_coordinator.dart:375` 的 `_hydrateToc` 获取目录后调用
  `SqliteOfflineRepository.upsertNovelDetail`（`sqlite_offline_repository.dart:708`）。
  后者在同步事务内删除该书目录，再逐节、逐章插入；目录相同也会执行，没有
  内容相等短路或增量更新。
- `sqlite_offline_repository.dart:157` 的 `reconcileIntent` 对每个目标章节单独
  查询任务是否存在。`novelia_download_coordinator.dart:184`、`:279` 还会先扫描
  整个下载意图的任务、逐项查询副本，再生成译文刷新候选。每轮刷新 20 章的
  限额在候选扫描之后，不限制这部分同步工作。只有译文缺失等候选才读取正文，
  不能说所有已完成章节每次都读取全文。
- 每本处理结束后，`main.dart:740` 的 `finally` 都调用 `_refreshLibrary`，
  即使阅读页仍在前台。`local_library_snapshot.dart:12` 同步读取全部续读、
  书签、下载意图、副本和任务，并逐本恢复完整目录，生成新的书架投影。
  某本发生一次更新，代价因此可能扩散到整个本地书库。

`async` / `await` 只让网络等待让出执行权，没有使后续 SQLite、对象构造与排序
在其他 isolate 执行。网络响应回来时，这些工作仍与阅读界面共享执行线程。
即使没有图片、没有新增章节，这条路径也存在；离线失败后的书架重建也会执行。
单纯拥有 40 本下载不会自动造成持续慢帧，关键是同步和刷新是否正在发生。

验证方向：用 40 本、每本数百至数千章的虚构已完成下载，在阅读纯文字时触发
一次普通恢复同步；把目录写入、任务扫描和书架投影分别标记，观察帧启动延迟。
处理方向：避免未变目录全量重写；批量查询任务状态；书架按变更合并更新；
将重的存储和解析工作迁出界面线程，保留离线阅读与后台下载能力。

## 2. 章节预取在界面线程读全文、重新序列化并校验

`novelia_reader_window.dart:303` 的 `_loadRequiredOnce` 在第一个网络等待之前
同步读取缓存；`:349` 的预取顺序加载后续 3 章，包在 `Future` 中仍使用同一
isolate。内存命中会避开这些工作，初次读取及离开内存窗口后的回读不会。

生产路径包含：

1. `sqlite_offline_repository.dart:1496` 读取并解码原文和全部译文 JSON；
2. `novelia_content_cache_adapter.dart:328` 恢复章节前校验全文；`:393` 将原文、
   各译文及元数据重新 JSON 编码、UTF-8 编码、计算 SHA-256；
3. 构造整章段落和译文映射；
4. 普通缓存还会触发网络刷新，响应后同步生成新缓存、编码并提交 SQLite
   （`novelia_content_coordinator.dart:706`、`sqlite_offline_repository.dart:1422`），
   随后执行缓存限额检查。

第 21 版已经包含文字解析、校验、预取和同步写入。第 22 版又在读取离线章节时
增加图片 base64 解码，会放大含图章节成本；同时已经改善了下载副本的读取策略，
不再对下载副本执行阅读窗口自己的网络刷新。这个改善不能消除同步读取本身。

验证方向：真实 coordinator + SQLite，分别用长篇纯文字、多个译源和含图章节，
覆盖冷读、预取与反向回读，采集解析、校验、对象构造、事务的耗时。
处理方向：将必要校验和正文转换放入后台执行，复用已验证的不可变章节；
不能用删除校验、限制下载内容访问来掩盖成本。

## 3. 竖向滚动会在手势中扩展内容并重新整理已加载章节

`reader_screen.dart:778`、`:837`：距离窗口边界不足 640 逻辑像素时扩展窗口，
每次最多增加 96 项；没有更多项时请求相邻章节。仅横向分页会等待交互结束，
竖向模式会在拖动或惯性期间应用结果。

`_validatedWindowChapters`（`:922`）与 `_rebuildStream`（`:353`）分别生成完整
目录的索引；后者还重建已加载章节的所有段落条目、稳定标识集合和位置索引。
追加章节（`:994`）把新增章节的全部条目纳入窗口，初始 128 项不是硬上限。

`_trimLoadedWindow`（`:1042`）以章节数超过 8 为条件，而且滚动未停时不裁剪。
因此长章节的段落总数没有固定上限，连续滚动时章节数也可暂时超过 8。
这不代表所有段落同时构建：Sliver 仍然惰性布局，已有段落 Widget 也有复用。
风险在于跨章时同步整理数据、增加分配和布局工作，不能夸大为每帧重建全文。

验证方向：长目录、每章数百段，标记扩窗、合并和裁剪，采集连续跨章的尖峰。
处理方向：复用稳定目录索引，增量维护窗口，给段落/字节规模合理预算，并保留
跨章连续阅读和锚点稳定性，避免通过延迟补充到空白页来换取性能。

## 4. 每帧锚点测量是持续拖动场景中需要单独检查的路径

`reader_screen.dart:1220` 合并同帧滚动通知后，在帧后调用 `_captureAnchor`。
`:1239` 遍历所有已挂载正文块，逐个取 RenderBox、做 `localToGlobal`，计算可见
比例，再求段内位置。滚动列表在视口前后各缓存 2 个视口（`:2011`），扫描对象
可能明显多于屏幕上真正可见的段落。

选择功能开启时，整个阅读区域还在 `SelectionArea` 中（`:2346`）。选择系统的
几何维护、短段落密度及中日双语排版是否占用主要时间，需要原生采样才能判断。
代码只能证明这些机制存在，不能仅凭 `SelectionArea` 就判定它有缺陷。

历史 Android PHN110 Profile 记录中的锚点采集中位数约 0.273ms，见
[此前性能记录](performance-optimization.md)；这不足以支持把它列为当前主因。
但针对用户所说的章内纯文字持续掉帧，需要重新以鸿蒙、密集段落和实际设置
验证，而不是只检查后台任务。

验证方向：无下载、无网络刷新、远离章界，改变段落密度、阅读模式和测试中的
选择开关，记录挂载数量、锚点扫描及布局时间；测试开关只用于归因，不作为
删除用户功能的修复方案。

## 5. 滚动停止后仍有同步落盘

`reader_screen.dart:2329` 在 `ScrollEndNotification` 后发布进度；
`main.dart:795` → `sqlite_offline_repository.dart:975` 同步事务保存续读、
副本最近阅读时间和最后路由。账号有历史同步能力且章节变化时，
`remote_history_sync.dart:54` 还会另写历史队列；网络完成后再同步删队列项。

它不是逐帧写数据库，普通滚动更新只观察锚点；也不是等待远程请求才显示正文。
但帧后同步事务可以占用下一帧的调度时间，尤其在连续短拖动、惯性被新手势
打断或存储变慢时。此前 Android PHN110 Profile 记录已有约 2.98–9.95ms 的
保存耗时，不能据此
推算鸿蒙耗时，也不能解释为持续整段拖动都在写入。

验证方向：真实账号接口的 fixture 与 SQLite，覆盖跨章、快速停止再拖动，
同时记录事务和 vsync→buildStart。处理方向：有序持久化队列、合并过期状态，
生命周期边界可靠刷新；须保护续读恢复，不能重新引入进度回退。

## 6. 插图解码后改变占位高度，可能产生布局跳动

`reader_body.dart:711` 为未知尺寸的插图固定使用 3:4 占位比例，首次解码后
`:770` 的监听器更新比例并立即 `setState`。`:797` 的 `AspectRatio` 随之改变，
没有与外层阅读锚点保持逻辑协调。这在第 21 版的网络图片路径中已经存在。

宽图、长图和占位比例相差大时，会改变 Sliver 几何；即便图片尚在屏外缓存
区域也会触发。需要区分帧超时、可见文字位移、滚动范围变化，不能统一叫掉帧。
此路径不能解释所有纯文字场景，也不能说明已解码、比例稳定的图片反复卡顿。

上一轮生成图片为 1600×2200，比例约 0.727，与占位的 0.75 太接近，覆盖不足。
验证方向：使用宽图和长图、受控首次解码，逐帧记录锚点的屏幕坐标和帧时间。
处理方向：提前保存图片尺寸、稳定布局，在尺寸变化时正确保持阅读位置。

## 已核对而未列为当前主因的项目

- `NovelChapter.translationState` 的回退分支会遍历全章，但生产在线适配器和
  缓存适配器均预先提供全部译源状态，正文正常读取走常量时间查询。不能把
  fixture 或未填状态的特殊构造误报成生产每段都扫描全文。
- `_hasVerifiedDetails` 首次可能恢复整本目录，但成功后会将书籍标记放入内存
  集合，后续不是每章都重复恢复目录。
- 文字 Widget 已按输入复用，滚动时控制条会隐藏；没有发现正文逐帧调用根
  `setState` 重建整页的证据。窗口扩展与数据刷新是另有触发条件的路径。
- EPUB 页内平滑翻页和跨章加载是另一条实现。此前 WKWebView 测量支持
  约 220ms 的动画完成节奏，第 21 版已有；没有证据表明它与网文竖向慢帧同源。

## 前一轮测量的覆盖不足与后续验证顺序

[macOS 测量](reader-performance-macos-2026-09-25.md)中的网文每章只有 6 段，
正文由 fixture coordinator 提供，没有生产缓存解析和校验，也没有真实账号的
历史同步。空闲文字/插图两组只记录 build/raster，没有记录帧启动延迟；补图
实验已经说明，只看两个阶段会漏报界面线程在帧外被占用的问题。

后续验证应按以下顺序逐项隔离，不以一次小样本通过代替实际阅读场景：

1. 真实缓存路径的长章节，完全无后台同步，先测章内持续拖动及跨章。
2. 保持同一本阅读内容，加入大书库的普通下载恢复，图片全部提前完整保存。
3. 单独验证停滚保存和首次插图改变高度；所有组均记录 vsyncOverhead、
   totalSpan、build/raster，并用原生 CPU 栈分解重操作。
4. Mac 定位后用鸿蒙发布模式复核，保留 60/90/120Hz 不同帧预算的解释边界。

本次核验为源码、版本对照和文档检查，没有将上述待测项写成已完成测试。
