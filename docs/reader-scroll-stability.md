# 阅读器滚动稳定性：观察与修正记录

## 2026-09-12：当前观察

用户在 HarmonyOS 网页小说连续阅读中遇到向上滑动时正文突然向下移动约两三行，
不确定与章末或预载有关。此前还分别修复过停止惯性滚动被误判为翻页、
章节刷新中断拖动等问题。它们不是同一个已确认的触发条件，但暴露了共同的
位置管理问题。

### 已验证的缺陷

- 页面尺寸未变化的窗口参数通知也会进入阅读位置恢复流程。本地测试在拖动中
  复现约 88 个逻辑像素的向下位移。窗口通知还可能涉及边距、系统手势区域等，
  不能把收到通知等同于页面尺寸变化。
- 真实尺寸变化会调用主动定位，打断拖动或惯性滚动。
- 尺寸校正等待布局期间，新手势可能已经开始，甚至在下一帧前已经结束。
  只检查“现在是否仍在滚动”不能识别已经过期的校正请求。
- 当前补丁过滤无尺寸变化的通知，并使尺寸校正让位于用户操作；滚动结束时
  沿用已有流程记录最终位置，不回放滑动前的旧位置。

上述机制有本地回归证据；手机的现有日志没有把窗口通知与阅读位置变化关联起来，
不能据此认定用户那次偶发跳动的唯一原因。用户已拿走手机，后续只做本地验证。

### 结构性观察

相关实现集中在 `app/lib/features/reader/reader_screen.dart`。

1. `ReadingPosition` 是用于进度、书签和重新打开小说的语义位置：章节、段落、
   段内比例。`_captureAnchor` 使用可见比例阈值选择段落，并把段内位置量化为
   0–1000。它不是可精确往返的屏幕几何位置；例如上一段只剩少量可见内容时，
   算法可能选择下一段。
2. `_restoreAfterLayout` / `_jumpToStableId` 同时服务主动导航和布局维护。
   后者不代表用户想去另一个位置，却可能执行 `ensureVisible`、`jumpTo`，
   把近似进度重新解释成对齐目标。
3. 章节刷新和章节窗口裁剪另有 `_settleWindowLayout` 路径，用屏幕几何位置
   重设列表原点。两种保位办法与多个异步状态判断并存，容易出现交错遗漏。
4. 纵向连续滚动和横向分页共用部分窗口及恢复状态。纵向列表已经使用 Flutter
   惰性 sliver 和固定中心；应先检查现有能力，再决定是否还需要手工维护。
   这不是删除虚拟列表或章节缓存限制的依据。
5. 现有测试涵盖多种具体场景，但通过这些样例不等于所有布局、加载和输入交错
   都满足相同的稳定性约束。

## 修正原则

- 正常阅读以当前视口为准；保存进度只观察和记录，不反过来驱动屏幕。
- 目录、书签、重新打开阅读位置及明确翻页可以发起主动导航。
- 内容或排版变化只维护当前可见内容的位置。几何补偿与主动导航分开，
  不用历史进度模拟“视口没有移动”。
- 新的用户操作使过期的布局校正失效；不能仅以当前是否仍在滚动判断。
- 不影响几何的外观更新不应进入排版恢复或显示恢复遮罩。
- 保留连续跨章、向前/向后加载、有界章节缓存、分页、书签、选择和进度恢复。
- 优先删除不必要的定位调用及重复状态，不新增滚动框架、计时器或常驻监控。

每步记录实际完成内容和证据，再继续下一步。若进一步精简窗口管理没有直接收益
或需要改变行为，留待单独决策，不把本次修正扩大成阅读器重写。
